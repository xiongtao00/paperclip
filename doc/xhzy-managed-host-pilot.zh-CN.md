# XHZY 项目级宿主执行试点

此入口替代按审批 ID 临时编写的执行脚本。它只在操作员主动启动时工作，适用于本机 local-trusted 实例。常规 Codex Runner 权限不变。执行器是宿主进程，不是 OS 沙箱；只为可信、已审阅命令启用。对不可信项目须另设隔离执行身份或环境。

## 配置与申请

1. CTO 选择一个合成数据试点项目，确认其公司、项目、申请员工和独立审阅员工的 ID。建立验证任务。默认由审阅员工持有；启用 autoAssignReviewer 后可由申请员工持有，由执行器交接。登记文件、脚本、依赖和状态目录放在受信任的宿主位置，不允许任务写入或替换。执行器只校验登记的可执行文件本身；若它解释脚本或读取项目构建，操作员须先冻结并审阅这些输入，不能给可写工作区里的任意脚本常驻授权。
2. 准备一个 JSON 登记文件，字段为 companyId、projectId、requesterAgentId、reviewerAgentId、cwd、executable、executableSha256、args、timeoutMs。可选 preflightArgs 是同一个可执行文件的短预检参数（最多 30 秒），artifacts 是允许回传的文件名列表。可选 autoAssignReviewer: true 也纳入审批哈希；旧审批不自动获得分派权限。工作目录和可执行文件使用真实绝对路径，拒绝符号链接映射。命令参数只从登记文件读取。试点先选固定、无模型的空白页或合成冒烟命令；需要端口、Chromium、构建来源或模型预算时，把它们写成登记入口的预检；预检失败不执行主命令。
3. 运行下方 identity 命令。申请员工用 Paperclip 原有的董事会审批能力，为该任务提交 request_board_approval；载荷包含 kind、recipeHash、issueId，并写明实际命令、风险范围、预算、预期产物。链接且只链接那个任务。董事会核对描述和登记身份后批准。
4. 操作员启动 worker。它只读取已批准的记录，并核对公司、项目、链接任务、申请人、审阅人、命令身份。批准前不会派发。不要把此进程开放到远程或使用普通 agent 令牌。

```sh
node scripts/managed-host-execution.mjs /absolute/operator-recipe.json /absolute/private-state --print-identity
node scripts/managed-host-execution.mjs /absolute/operator-recipe.json /absolute/private-state --watch
```

状态目录权限为 0700，只运行一个 supervisor。每次审批用独立子目录记录 receipt.json 和有大小上限的 execution.log。重启必须使用同一状态目录；不要为重试而删除旧记录。如果进程在执行中消失，收据标为待核对，先确认进程和原件，不自动重新运行。旧路径和日志不清理。禁用时停止 worker 并撤回未消费的批准；停止 worker 不保证已经脱离进程组的子进程被清理，需按宿主进程管理办法处置。

## 回传与验收

预检和启动阶段会写入原任务；结束后记录退出状态、审批／执行身份、缺失产物以及附件链接。登记入口把允许回传的合成证据写入 PAPERCLIP_ARTIFACT_DIR。最多登记 10 个顶层文件，每个不超过 8 MiB，只支持 JSON、PNG、ZIP 和 TXT；不会上传未登记的文件、符号链接或宿主原始日志。严禁把真实数据、密钥、模型请求正文或未经审查的 trace 列入白名单。

附件通过 Paperclip 自带的任务附件权限交接，不依赖 QA 访问宿主路径。结束时冻结文件 SHA-256，上传前复核，与服务端回执不一致则不发起 QA 唤醒。回传出错可从持久收据续传；同名同哈希附件不重复上传。缺失产物会列在原任务，不能据此签核。

收到执行结果后，worker 请求带幂等键的 QA 唤醒；如果被跳过，则写回原任务并留给负责人核对阻塞。不自行改变任务状态、关闭任务或代替独立 QA 签核。启用自动分派时，RE 发起审批后将原任务留在 in_review 并结束自己的运行。执行器先回传证据，再通过 Paperclip 的受保护更新将任务交给登记 QA。若项目、状态版本、负责人或执行锁发生变化，服务端拒绝交接；执行器核对现状，不强行覆盖。未启用时，试点任务仍需预先分配给 QA。独立依赖和阻塞不能被执行结果自动解除。

本地开发验收：运行 node --test scripts/managed-host-execution.test.mjs。用合成进程覆盖未批准和错范围拒绝、只跑一次、恢复回传不重跑、未完成认领不重跑、失败预检不启动、附件哈希与链接、缺件及跳过唤醒、符号链接拒绝。实际公司试点需配置登记入口，按 P01–P05 走一次董事会审批和 QA 签核。未消费任何历史批准。

## XHZ-15 实例试点结果

现有审批触发了合成浏览器运行，退出码为 0，PNG 和 JSON 均回到原任务，QA 已接续并核对 JSON 的合成标记及零模型调用。独立唤醒回执曾记录跳过；不能据此推断 QA 从未运行。

用本机董事会访问原 PNG 附件成功；下载的 900 × 500 PNG 与任务附件 SHA-256 a8831cbea4a85d7f8cb608bac591a87c2d0f6bb87f4099fdcd0759a7872ecab6 一致，人工视图确认能看到试点标题和合成页面提示。无需重跑。QA 的原会话仍无法查看图像，尚未独立签核。需在相同 QA 身份区分内容访问与图像呈现能力，再补齐受授权的图像查看；董事会能读并不能证明 QA 能读。该试点不计为完整验收通过。

## XHZ-16 员工自行申请试点结果

Release Engineer 在原任务发起审批，申请人记录为该员工，无董事会申请人。命令身份和单一关联任务匹配登记。操作员将任务交给 QA 后，董事会批准一次；执行退出码为 0，PNG 和 JSON 回传，无缺件。QA 核对平台哈希及合成 JSON 的 modelCalls=0 后签署通过。未重复运行。

执行器的独立唤醒回执为 skipped，但 QA 实际已接续完成。判断接续应结合任务运行及 QA 签核，不能把单条跳过回执当作无人处理。此轮仍有操作员执行一次 QA 分派；并未验证分派自动化、Runner 原生图像查看、生产项目体验关卡或全部故障演练。


## 自动分派的开发验证

守卫在路由入口和数据库任务锁内检查，只有原申请人持有、无运行或签出锁、且版本匹配的审核任务可交接；不能在同一个请求夹带关闭任务等动作。临时 PostgreSQL 上并发发起两次交接，只有一次提交，另一次返回冲突。执行器测试模拟分派已提交但 HTTP 回执丢失：恢复后只补 QA 唤醒，不再次分派或重跑。旧试点审批没有开启自动分派，没有被重放。此功能仍待本机实例加载并用新任务验证。

## XHZ-17 阻塞与修复

批准后，普通审批唤醒了 RE；它在结果到达前把任务标为 blocked，导致执行器无法认领。恢复原任务为 in_review 后，同一审批执行一次、退出 0，PNG 和 JSON 均已回传。进度评论也可能唤醒 RE，所以执行成功不等于完成分派。已把任务交给 QA 并排为待办，没有重新批准或执行。

代码已区分宿主执行审批与普通员工接续：前者交给执行器，不提前唤醒 RE。执行器用不触发员工唤醒的进度评论记录阶段，先回传原件，再用带项目、负责人、状态版本及执行锁检查的事务交接 QA 待办。普通审批、普通评论的唤醒行为保留。

XHZ-17 实例还存在旧 RE 运行的 execution_reconciliation_required；该保护与宿主执行成功分开，不自动清除。新版改动通过审批与任务接口回归、静默进度及执行器测试；尚未在运行实例加载及重新验证完整自动分派。

收口：旧 RE 运行终态为 failed，当前 QA 不是该运行负责人，保留防重放保护。关联 QA 子任务 XHZ-18 对既有 PNG、JSON 哈希及 synthetic=true、modelCalls=0 独立核验通过。结论已回写 XHZ-17，两个任务均关闭；未重跑或重新批准。此轮不计自动交接通过。修复代码尚未加载；待员工空闲后再重启和复验。

XHZ-19 使用已加载静默进度保护的实例和更新后的自动分派 worker；原 XHZ-17/XHZ-18 已完成的执行证据不重放。此轮检验批准后不提前唤醒 RE、证据到达后才将原任务交 QA 并排入待办。等待批准与真正执行分别记录。

XHZ-19 最终结果：审批显示 delegated，执行成功退出 0，PNG/JSON 两件原件均回传，任务自动分派给 QA，QA 签核完成。单独的显式唤醒返回 skipped；这条回执不能代替任务运行与验收状态。执行器已在收到 skipped 时核查交付后同任务、同 QA 的排队或运行记录；有证据时记 already_scheduled，不再误报成阻塞。无证据时保留“未确认”，不重复执行。

开发故障验证共 9 项通过，新增真实子进程超时终止、终态收据重启不重跑，以及 QA 已经由分派启动时的接续判定。尚未演练生产项目的执行器断电或长时间断网；不能用合成试点替代真实产品的体验验收。
