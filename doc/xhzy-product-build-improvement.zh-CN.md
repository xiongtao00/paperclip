# XHZY 产品构建与交付改进实施方案

状态：公司流程 v1 和八个岗位条款已应用并读回核验；项目级宿主执行器、阶段进度、附件回传和 QA 唤醒已有实现；合成实例试点已签核；生产项目体验、故障演练与推广仍待验收。适用于 XHZY 今后的产品项目。一句话记账仅为复盘样本，本方案不安排对该应用的改版，也不授权扩大运行权限、采购或新增真实模型调用。

## 决策与优先级

保留固定版本、独立 QA、确认前零入账和凭证隔离。优先补两条链路：**执行授权能变成可见的运行和结果；用户体验在实现前就有可验收标准。** 两条线可以并行准备。暂不增设兜底员工、不换模型、不全局放宽 Runner。

这次受限 Runner 的 Chromium 启动失败，而获准宿主能创建页面；这证明执行上下文有差异，不足以认定所有本机 Runner 不可用或定位某个上游 bug。审批未自动触发执行和唤醒被跳过是已观察到的现象；一次性宿主脚本绕过了本轮阻塞，但没有形成可持续调度。另一个独立改动是本机受管 Codex 连接对全局 CRS 配置的误判修复，应单独登记、测试和回退。

最终非模型 38/38 与追加真实页面 8/8 是有效的功能证据，不能外推为易用性、实机听写或长期可靠性。复盘记录的约 22 小时 52 分是日历跨度，不是工时；未取得完整账本，浪费的 token 和金额不能精确估算。

## Paperclip 执行闭环

### 已实现的审批回执

审批详情从原有活动记录读取本次决策后的申请人唤醒结果，区分已受理、跳过、失败和无记录。已批准的页面即使刷新也不会一律宣称员工已收到通知；只展示调度结果，不暴露审计诊断或误报执行成功。旧记录写成“已排队”但没有运行 ID 时显示为跳过。

这一步是 P01/P04 的可见性基础，不创建宿主执行权限。下一步是接入项目级受管执行器，让实际执行 ID、阶段、证据签收和恢复结果在原任务中可追踪，再做 P01–P05 试点。

**开工预检。** CTO 和 RE 用未来执行任务的同一身份、工作区、HOME/TMPDIR 验证仓库读写、依赖安装、子进程、loopback、Chromium 创建页面及证据签收。分别记录网络、应用认证、员工认证与文件权限；遇 401 先用生产一致加载器核对配置，不先要求用户换 key。预检使用合成数据和无模型模式。任一能力不通，可以继续做需求和设计，但不能承诺完整自动验收。

**审批范围。** 首选 Paperclip 可用的受管执行机制；不足时由 CTO 提交项目级本机接入方案。预授权可覆盖指定项目、命令模板、审阅过的执行包、有限网络和时限内的常规无模型测试；包变化仍需审阅及绑定哈希，但范围不变时不必重复请董事会审批。新增外部服务、模型调用、敏感数据、费用或扩大宿主访问，才重新确认授权。入口不接受任意 shell 或未经审阅的代码；不得全局放宽 Runner。

**状态与恢复。**

| 状态 | 必须可见的证据 | 下一步责任 |
|---|---|---|
| 待审批 | 原任务、固定产品与包身份、执行范围、预算、有效期；执行入口可调用 | 董事会批准或拒绝 |
| 已批准待调度 | 审批 ID、队列回执，或明确的不可调度原因 | CTO 排查，CEO 跟踪 |
| 执行中 | 唯一执行 ID、阶段、最后进展及停止条件 | RE 或受管执行器 |
| 已结束待核验 | 退出码、实际用例计数、来源收据、证据清单 | QA 签收、独立核验 |
| 需修订或已验收 | 逐项结论和未测范围；修订给出差量与负责人 | PM／CTO 处理差量，CEO 收口 |

用审批 ID、包哈希和目标项目绑定唯一执行；重启和重复派发先对账，不能因收据暂不可见就重复执行。输出目录按执行 ID 独立分配；静态发现和动态结果分开。证据区有明确保留期，记录产品 SHA、锁文件、工具版本、BUILD_ID、模式及阶段退出码。自动交接白名单原件和哈希，QA 从自己的工作区签收。证据缺失先找原件；构建失效时按适用授权重建并生成新来源记录。回传后核对唤醒回执，被跳过时显示原因及接手人。

| 验收 | 演练与通过条件 |
|---|---|
| P01 审批触发 | 批准前无进程；批准一次后有唯一运行、可见进度和原任务收据；QA 接续 |
| P02 重复及重启 | 重放同一审批、执行器重启后不重复安装、执行或调用模型；状态不明时明确待核对 |
| P03 环境失败 | 人为制造端口占用、缺浏览器或构建失效；重阶段前拒绝，不杀未知进程，给出具体修复或差量审批 |
| P04 证据与恢复 | 模拟缺原件和唤醒被跳过；能补交原件或明确缺口，不重跑；原任务显示原因和负责人 |
| P05 越权与回退 | 改包哈希、项目、命令或预算时拒绝；禁用试点入口后原审批和证据保留，其他项目不受影响 |

## 团队配置与构建流程

以[公司构建流程草案](company-build-process-draft.md)作为统一来源。角色说明只写决策规则、交付物和交接对象，引用流程版本；项目启动单写具体范围、权限、模型预算、用例和验收人。实施先读取当前提示词，提交带 baseRevision 的最小差异。提示词不能代替审批、执行、预算和收证的技术控制。

| 角色 | 应写入的责任与行为 |
|---|---|
| CEO | 对交付闭环负责。阻塞须记录影响、事实、具名接手人、解除动作、恢复证据和下次检查事件。无可点审批，不说等董事会；无接单记录，不说平台已接手 |
| CTO | 对技术恢复负责。先分层判断环境、工具、产品或模型契约；审生成后的配置与实际执行边界。必要时调用受管诊断，不把排障交给董事会 |
| PM | 冻结需求到证据的矩阵及用户体验门槛，拥有体验退回权；新增用例要解释为何必要、哪些证据可复用 |
| 设计 | 交付核心路径、文案、空态和失败态，手机优先并核对实物；不将视口图当实机结果 |
| Staff | 按生产一致契约实现，交固定版本、复现和受影响面；不自行签独立 QA |
| QA | 先冒烟再扩跑；区分通过、产品失败、脚本失败和未运行；真实、mock、视口、实机分别记录 |
| RE | 用同身份预检、校验运行身份、报告进度并交齐原件；失败时留证，不用重复启动替代排障 |
| 内容运营 | 评审产品措辞和发布说明；本地存储、第三方处理及已测设备按事实披露，不参与日常技术调度 |

试点用四个历史情境验收角色条款：批准无执行 ID、静态清单占结果路径、变量引用导致 401、探针在业务断言前失败。要求给出正确分类、唯一承接人和下一步，不声称已通过，不产生无变化的重复唤醒。测试默认顺序是单项冒烟、差量回归、最终验收；同一失败在代码、输入和环境不变时停止重跑。开发、QA、审批、执行与交付结论分开记录。

## 跨项目的产品体验关卡

PM 在立项时确定目标用户、使用环境和三条最重要的任务；不沿用上一个项目的页面、功能或测试数量。设计在开发前交付适用设备的主流程、空态、错误态和恢复方式，并明确哪些信息需要用户看到。重要隐私、费用和不可逆操作用用户能理解的语言说明；诊断术语放在必要的详情处。

| 阶段 | 责任与通过条件 |
|---|---|
| 开发前 | PM、设计交可审阅原型与文案；QA 将核心任务、失败恢复和数据风险写入验收矩阵 |
| 实现中 | Staff 对照原型实现；新增技术限制应明确影响，并由 PM 决定是否调整体验 |
| 交付前 | 未参与实现的人按任务独立操作，记录是否完成、需要提示、出现误操作以及恢复方式；PM 签体验，QA 签功能和数据安全 |
| 范围披露 | 桌面、移动视口、真机和辅助技术按项目所需分别核验；未运行或未测的项目不冒称通过 |

试点建议至少两位未参与实现的人走完核心任务，以无需指导、无危险误操作为门槛。真实模型、浏览器或实机等关卡仅在项目需要时启用，不给所有任务套同一份重流程。

## 度量与复盘回写

CEO 每次试点记录计划外审批数、审批到实际启动的耗时、无人承接的阻塞时长、相同条件下的重跑次数、证据缺失数和核心任务无指导完成率。用量按项目运行与应用服务分列；报告已计价、未定价和待结算。模型测试按包约定请求上限、重试和停止规则。不用公司累计金额冒充项目费用，也不在缺少基线时声称节省百分比。

推广门槛：一次批准对应一次可追溯执行、没有无人承接的阻塞、无需董事会代跑或搬证据、同条件重跑被拦截、核心体验通过。失败只修失败环节并复验；回退时恢复旧提示词 revision、关闭项目执行入口、保留原审批和证据。只有多个项目显示平台维护已挤占 CTO 职责，再考虑专职平台岗位。

整改映射：A01/A02/A05 → 预检与生产一致诊断（E02）；A03/A06/A07 → 运行身份、证据与审批接续（E01/E03/E04/E05/E06）；A04/A08/A11 → 冒烟、停止空转与成本台账（E07/E08）；A09/A10/A12 → 差量矩阵、权威启动说明、体验和实机验收。
