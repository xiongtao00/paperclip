# 项目开工澄清与资源确认

CEO 收到需求后组织一次有产出的岗位评审，再由 CEO 统一向用户提问。用户确认方向、必要资源和授权之后，团队开始实现。此流程适用于新项目及足以改变交付范围的变更。

## 岗位评审

CEO 在原项目任务中给出已有需求与待确定事项，邀请实际相关岗位，以短咨询子任务异步完成一轮评审。各岗位最多提交五项问题，说明缺口、影响、推荐方案以及是否必须由用户决定。CEO 合并相同问题，团队自行解决普通技术选型。需求已经明确的小任务可以复用已有结论。

| 岗位 | 评审内容 |
|---|---|
| PM | 谁使用、解决什么问题、核心任务、优先级、成功标准与范围 |
| 设计 | 界面风格、交互偏好、使用设备、品牌与图片等素材 |
| CTO、RE | 新建或复用仓库、绝对路径与分支、已有文件保护、运行与交付环境、API和认证、权限、费用、数据与资源 |
| QA | 可验证的功能与体验标准、关键失败路径、设备覆盖及数据风险 |
| Staff、内容岗位 | 按项目需要补充实现约束、导入格式、内容来源和发布措辞 |

CEO 形成一份启动记录，保留来源任务与会议意见。首次评审完成后停止无新信息的重复咨询。

## 用户问答

每轮只问当前影响结果的少量问题，把相关问题合并。每题说明为什么需要用户决定，给出推荐选项及取舍，保留自填方式。已有回答、已有授权和用户明确交给团队的决定均予复用。

问题通过原任务的原生 `request_human_input` 保存，使用 `interactionKind=questions`、`resolverPolicy=human_only` 和 `continuationPolicy=wake_assignee`。表单使用 `payload.version=1` 与完整的 `questionSet`，其 schema 为 `paperclip.question_set.v1`。开放问题用 `answerMode=text`；选择题用 `single_select` 或 `multi_select`，至少两个有意义的选项，并开放自填。原生工具的说明及运行中的 schema 是参数权威来源。

保存后核对真实 interaction ID 与待答状态，把卡片链接留在原任务。CEO 保持负责人，以 `in_review` 等待，用户答复后由平台唤醒。只有当前确实依赖的答案才阻止相应工作，等待期间可以继续独立且已获授权的核查。新的回答仅引出必要的后续问题。

问答覆盖以下适用事项。

- 产品目标、核心用户、功能范围、优先级、偏好及验收方式。
- 仓库新建或复用、绝对路径、分支、已有代码保护、Paperclip工作区绑定。
- API服务、数据、图片、品牌与其他素材的用途、来源、获取入口和允许的使用范围。
- 密钥是否已有受控引用、调用额度、预算、外部访问、部署和真实数据处理授权。

API KEY、令牌和私密数据走 Secrets、连接或受控资源入口。问答、任务文档及仓库只保留必要的资源引用。团队核验资源是否可用时只记录状态。需要正式审批的费用、权限或发布操作，先生成具体审批卡，问题回答与正式审批分别保留。

## 启动记录与开工

启动记录采用原任务的版本化文档，至少包含以下内容。

| 项目 | 需要保存的事实 |
|---|---|
| 目标与范围 | 用户、要解决的问题、核心任务、优先级、范围及不做项 |
| 产品偏好 | 关键页面、交互、文案、风格和素材引用 |
| 验收 | 功能与体验矩阵、设备范围、独立签核人 |
| 代码与运行 | 仓库位置、分支、工作区绑定、预检结果、交付入口 |
| 资源与授权 | 数据/API/密钥等资源的受控引用、可用性、费用与权限边界 |
| 决策与责任 | 问答卡和回答引用、具名负责人、待决定项与恢复事件 |

每项标记为用户已确认、用户授权团队决定或待回答。CEO 核齐影响实现方向的需求、必要资源与授权后发布可开工结论，再分派实现。需求变化时更新文档版本，评估受影响的授权和验收项。

对 XHZY，未来项目优先使用 `/Users/alex/Code/opc/ai-company/xhzy-projects/<项目名>`，作为建议代码位置交用户确认；用户授权团队选择时记录采用的绝对路径。现有项目按已绑定位置继续工作。

## 验证方式

使用一个存在明确需求缺口的小项目，检查岗位意见是否先被汇总、问答卡是否真实出现、CEO是否保持原任务负责人、回答后是否自动接续，以及启动记录能否追溯到回答。只在开工条件满足后检查开发、独立QA、体验签核与最终交付。用户未回答时保持待答，不能伪造回答或把经过的时间视作确认。
